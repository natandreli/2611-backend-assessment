# Assumptions

> The scenario is intentionally incomplete. Record every assumption you needed to make, and the part it affects.

| # | Assumption | Why I needed it | Part(s) affected |
|---|---|---|---|
| 1 | The payment lifecycle is **monotonic** for the three providers: `Pending` → `Captured` or `Failed` → (`Captured` only) `Partially refunded` → `Refunded`, where a refund may also be full from the start. No provider moves a payment backwards (for example, from refunded back to captured). If a provider introduces such a transition, the state machine is extended for that transition. | The specifications describe each lifecycle but never state that it cannot regress. The ordering strategy (FR5) ranks states instead of trusting provider clocks, which is only safe if states never go backwards. | A, B |
| 2 | A failed charge never becomes captured. When a payer retries, the provider creates a **new** charge or transaction with a new identifier, which is a new payment. | No specification describes a failed payment becoming captured. Andina describes `PENDIENTE` → `APROBADA` or `RECHAZADA`, and only an approved transaction may later become `REVERSADA`. The state machine treats `Failed` as final. | A, B |
| 3 | Andina Pay only operates in Colombia. A `transaccion.referencia` made of exactly 9 digits is normalized to `POL-CO-<digits>`. References are also trimmed and upper-cased. Any reference that does not match `POL-CO-` followed by 9 digits after normalization is **not** guessed: the notification is accepted, **parked** for Operations and not sent to Salesforce. | Since Andina API 2.3 (2026-11-28) the reference arrives exactly as typed by the payer, and Andina asks merchants to normalize it. Guessing a policy number could attach a payment to someone else's policy. | A, B, D |
| 4 | The API Manager forwards the request body **byte for byte** and keeps the providers' signature headers. | Every provider signs the raw body. Any re-serialization by the gateway would break signature verification (FR1). | A, B, C |
| 5 | The API Manager assigns a correlation identifier to each incoming request and forwards it in a header. If the header is missing, the intake generates one. | NFR7 requires end-to-end traceability, and the identifier must exist before the body is read so that rejected requests are traceable too. | A, B, D |
| 6 | Downstream consumers (Finance, Notifications) do **not** need payer personal data in the canonical event. When they need customer details, they look them up in Salesforce by policy number. | Data minimization (NFR6): every subscriber, queue and dead-letter queue that receives the event would otherwise hold copies of names, national IDs and emails. | A, B |
| 7 | Quetzal `charge.refunded` carries the **cumulative** refunded amount in `amount_refunded`. When `amount_refunded` equals `amount`, the payment becomes `Refunded`. When it is lower (**partial refund**), the canonical status is `PARTIALLY_REFUNDED`: it is written to Salesforce as `Captured`, and the payment is listed for manual review by Operations, who receive a daily summary of pending reviews (not an urgent alert: the policy is not affected while the payment stays `Captured`). As a follow-up, the Salesforce team would be asked to add a `Partially_Refunded` status to the picklist. | The `Status__c` picklist has no partial-refund value, and the integration cannot change it. Marking a partial refund as `Refunded` could make the Salesforce flow suspend a policy that is still covered (for example, when only an overpayment was returned). The specification does not say why a partial refund happens, so a person decides. | A, B, D |
| 8 | Andina `REVERSADA` and Austral `PAYMENT_REVERSED` always reverse the **full** amount. | Neither payload carries a refunded amount, and the samples repeat the original amount. | A |
| 9 | Retention of the integration's own store: **90 days** for the per-notification processing history and **13 months** for the payment state (needed to recognize late duplicates and stale notifications). These values are a proposal to be **validated with Customer Support, Operations and Legal**. No specific legal retention period was provided for this data. Salesforce remains the system of record for long-term payment records. | The payment state must outlive the latest possible reversal, or the state machine could no longer reject a late notification. The processing history supports incident and complaint investigation. | A, C |
| 10 | The API Manager enforces HTTPS and applies **rate limits** per provider endpoint, so a flood of requests (for example, with invalid signatures) is throttled before it reaches the intake. | The intake records every request, including rejected ones, for Operations (FR7). Without a rate limit, an attacker could fill the database with rejected requests. | A, C |
| 11 | For Quetzal `charge.failed`, the event time `created` is used as the time of the state change (`statusChangedAt`). | The `charge.failed` payload has no failure time (`paid_at` is `null`). A failure is final, so a small difference between both times does not change the result. | A, B |
